# Retrospective: WardStock → Lucius

A phase-by-phase account of how this project actually evolved — what was assumed at each stage, what got built, what turned out to be wrong or missing, and how each finding changed the next phase's starting assumptions. This is a companion to `godaddy/PROJECT_PLAN.md` and `homeassistant/PLAN.md`, not a replacement — those two are the detailed decision logs (why a specific line of code exists); this is the narrative of how the whole thing got here. Individual debugging back-and-forth is deliberately compressed out — what's kept is what was assumed, what turned out to be true, and what to remember.

---

## Phase 0 — Context: therapeutic journal work (parallel, not part of the system)

Before any code existed, a separate work stream reviewed Ward's CBT/therapy journals for gap analysis alongside his therapist. Unrelated to the software described below, but it's the reason WardStock's Incidents feature is shaped the way it is — anxiety and cardiac episode tracking, not generic health logging.

## Phase 1 — WardStock: a single-user PHP app on GoDaddy

**Starting assumptions:** single user (Ward only), GoDaddy shared hosting, PHP + MySQL, deliberately no framework and minimal dependencies — a choice that held for the entire project and shaped several later decisions (e.g. no composer/PHP library for anything, preferring vanilla code even when a library would have been faster to reach for).

**Built:** Incidents (anxiety/cardiac episode logging), Daily Log (sleep/exercise/caffeine/alcohol/medication/mood), Medications (dosage history, not just current state), Therapy (sessions + recurring schedule + since-last-session report), a 7-day dashboard, JSON Export/Import.

**Conventions established here, still in force:**
- Versioning: `Major.SQL.Code` — SQL number is the only one the database itself needs to track (`db_version` stores just `Major.SQL`), so a code-only release never requires a database step.
- Zip packaging: four folders (`app/`, `config/`, `sql/`, `setup-delete-after-use/`), with `config/` deliberately excluded from routine re-uploads so a careless "upload everything" can never overwrite real credentials with a blank template.

**Oura Ring integration — the first real hard-won lessons of the project:**
- Requesting the wrong OAuth scope produces a silent 200 OK with empty data, not an error — easy to mistake for "no data exists."
- A same-day query window misses sessions that started the evening before crossing into UTC; the fix (query `date-1` to `date+1`, then filter results to the exact day) took real debugging to find and has been reused as-is in every later Oura-touching flow.
- Oura's actual OAuth scope string format doesn't match its own documentation.
- Generic "something went wrong" error messages were replaced with rich diagnostic pages (`oura_test.php`) showing raw HTTP codes and response bodies — this diagnostic-first instinct became a recurring pattern for the rest of the project.

## Phase 2 — Planning a Home Assistant migration (before it had a name)

**Starting assumption, stated directly and never revisited:** WardStock stays exactly as-is — always-reachable, simple, the thing Ward actually opens day to day — because incidents happen away from home, not just when near a home server.

**Decided:** Home Assistant becomes a background sync/analytics engine, not a replacement. Node-RED chosen as the sync engine specifically because it was new territory worth learning, not because it was the obviously easiest choice. Auth tokens live in a config file on the HA side. HA is meant to be usable as a disaster-recovery source of truth if GoDaddy's database is ever lost — a goal that later forced pulling *full* records (including free text) rather than just structured summary fields, and eventually forced including medications after that gap was found (see Phase 4).

## Phase 3 — Renamed to Lucius, restructured as two pieces

Ward asked to fold the HA plan into the same project rather than treat it separately, and to mark the change with a major version bump and a new codename. Restructured into `godaddy/` and `homeassistant/` as two clearly separated pieces of one project, each with its own README and plan document, with a short top-level README explaining why the split exists (same "always-reachable vs. background processor" reasoning from Phase 2, now made explicit as an architectural principle rather than just a planning note).

## Phase 4 — Building the GoDaddy-side API surface for HA to talk to

**Built:** three new token-authenticated endpoints (`oura_push.php`, `pull_manual_data.php`, `status.php`), a new `ha_sync_log` table logging every call with a real status-code taxonomy (not just success/fail), and — deliberately — refactored existing logic into shared functions rather than duplicating it (the merge-safe upsert, the export-record builder), so the new endpoints and the existing human-facing pages stay in sync by construction.

**Found and fixed here:** Ward asked directly where medications were being stored on the HA side, and the honest answer was "nowhere" — the disaster-recovery pull never included them. Worse, `import.php` had no handler at all for a medication record type, meaning even fixing the pull side wouldn't have been enough; a real restore attempt would have silently dropped every medication. Both fixed together. **Lesson carried forward:** "add a feature" and "confirm the whole path actually works end to end" are not the same check — this pattern (a plausible-looking feature with a silent gap somewhere in its actual round trip) recurred more than once later.

## Phase 5 — Building the Node-RED flows: a long run of real bugs found only by actually running things

This phase is the largest single source of findings in the whole project, precisely because none of it could be verified without a live HA/Node-RED instance. Each item below was a genuine, confirmed bug — not a style choice — found on a first real test, not anticipated in advance.

**Bug 1 — the `ha-entity` node was deprecated.** The original design used a generic node to set HA helper entities. Node-RED itself flagged it as deprecated on first real use. Root cause: setting a helper entity is actually a *service call* (`turn_on`, `set_value`, `set_datetime`), not a direct state write — the original design modeled the underlying mechanism wrong, not just picked an old node. Fixed with `api-call-service`, chosen specifically because it's the palette's core mechanism, not a convenience wrapper likely to be deprecated again.

**Bug 2 — `require('fs')` doesn't work in Node-RED Function nodes.** Not a version issue — Function nodes have never exposed Node's module system in a stock configuration. All file I/O (secrets, disaster-recovery archive) was rebuilt around core `file`/`file in` nodes instead, which need no special configuration at all.

**Bug 3 — `/config` is not `/config`.** The single most confusing bug of the project. Node-RED's own add-on has its own internal working directory that's also called `/config`, entirely unrelated to Home Assistant's real configuration folder (which Studio Code Server edits under the same name). Found by direct `exec`-node filesystem inspection rather than guessing — `ls -la /` from inside Node-RED's own container revealed `/share`, HA's actual purpose-built mechanism for sharing files between otherwise-isolated add-ons, which is what all secrets/archive paths were pointed at instead. **Lesson explicitly written down at the time and worth repeating here:** never trust a path or hostname across two different HA add-ons without verifying it from inside the actual container that needs it — "it works from Studio Code Server" says nothing about whether it works from Node-RED.

**Bug 4 — GoDaddy rejected a token that was actually correct.** A real, separate server-side bug: many Apache/FastCGI shared-hosting configurations strip the `Authorization` header before PHP ever sees it. Fixed with the standard `.htaccess` re-injection rule, plus defensive fallback header-reading in `check_api_token()`. This fix was necessary — but not sufficient.

**Bug 5 — the token was never actually in the secrets file.** After Bug 4's fix, the same symptom (401, "token rejected") persisted. Rather than guess at server configuration a third time, the investigation shifted to a disciplined sequence of small, disposable, delete-after-use diagnostic scripts — each answering exactly one question (does the header arrive? does the real `check_api_token()` logic pass when called directly? does Node-RED's own HTTP client succeed with a hardcoded known-good token?) — narrowing the search systematically rather than re-guessing broadly. Root cause: `lucius_secrets.json` still had the literal placeholder sentence from its own `.example` template. The config-file check had reported this field as "present" the entire time, because it only verified non-emptiness, not correctness. Fixed by tightening that check to reject known placeholder language and validate the token's exact expected shape. **This is the clearest single lesson of the whole project:** a config check that only asks "is this non-empty" will not catch "is this actually the right value" — worth remembering for any config field added later.

**Bug 6 (parallel investigation) — InfluxDB 1.x vs 2.x.** The first InfluxDB add-on installed turned out to be version 1.8.10, which uses an entirely different data model (databases + username/password, no orgs/buckets/API tokens) than the 2.x design the whole integration was built around. Confirmed directly via `/health`'s own version field rather than assumed. Rather than rebuild the integration around the older API, Ward chose to move to a real 2.x add-on instead — which took two more rounds of correction (an add-on's *code* repository is not the same as its *catalog* repository that Supervisor actually needs; a `my.home-assistant.io` redirect link doesn't work without that separate service being linked, and isn't necessary at all — the plain manual "Add-on Store → Repositories" path works directly). **Fully confirmed working end to end since**, including the parts that were originally left as generic/assumed steps: org/bucket creation through the add-on's own onboarding wizard (no separate "Data" UI tab the way a fuller InfluxDB UI might suggest — first-run setup handles it), scoped API token generation, and the add-on's own config YAML (`ssl: false` is what's actually needed, confirmed, not just plausible). Full real steps written up in `homeassistant/INFLUXDB_V2_SETUP.md`. One caveat surfaced along the way, not a bug but worth tracking: the add-on itself hasn't had a commit since 2022 per its own Info tab — works today, just not something to assume gets maintained going forward.

## Phase 6 — New default methodology, adopted directly because of Phase 5

After enough real bugs were found only by running things live, Ward and Claude adopted a standing rule: **every live Node-RED flow gets a companion test/validation flow, built and kept alongside it** — not deleted after use like the earlier one-off PHP diagnostics, since Node-RED's package ecosystem has repeatedly proven unpredictable enough (an undocumented read API, a deprecated core node, a module system that was never available) that re-verifying is a recurring need, not a one-time cost.

**First real application of this rule:** `node-red-contrib-officedocs`, the library chosen to parse Ward's smart-scale `.xlsx` exports for the not-yet-built Body Composition feature. Package chosen specifically for being actively maintained (3 months old vs. ~4 years untouched for two alternatives) after that recency gap was checked directly rather than assumed. Its actual read API (`read` then `readRange`, exact field names `params.source`/`params.range`/`params.sheet`) was fully unknown going in and confirmed entirely through a real test flow: ground-truth package inspection first, then real errors correcting each wrong guess one precise field at a time, rather than broad re-guessing. Fully resolved and documented for reuse.

## Phase 7 — GitHub, and a real credential exposure caught and fixed

The repo was pushed to a public GitHub remote (`echild07/wardstock`) and GitHub Actions set up via `/install-github-app`. Checking the connection surfaced two separate, real problems, neither anticipated going in:

**Problem 1 — `godaddy/config/config.php` was committed and public.** The real DB password, `APP_SECRET`, and `API_SYNC_TOKEN` were sitting in the initial commit, reachable via GitHub's API the whole time the repo was public. Found by directly checking the repo's visibility and fetching the file's live content — not assumed from the local `.gitignore` situation alone. Fixed in layers, all in one pass rather than partially: `APP_SECRET`/`API_SYNC_TOKEN` regenerated (DB password rotation is Ward's own action, in cPanel — can't be done remotely), `.gitignore` added, and the file scrubbed from *all* git history with `git-filter-repo` (installed via `pip`, since GoDaddy's config file was in the very first commit — a simple `git rm` wouldn't have touched history), then force-pushed. Verified clean by grepping every blob in the rewritten history for the old secret strings — zero matches. **Honest caveat kept in the fix itself:** rewriting history stops future exposure via GitHub's UI/API, but can't prove nothing was scraped during the window the repo was actually public — that's the real reason credential rotation matters independent of the git cleanup, not just belt-and-suspenders.

**Problem 2 — SSH push was failing, for two independent reasons stacked on top of each other.** First, the local SSH key was passphrase-protected with no agent running — fixed by starting the Windows `ssh-agent` service and unlocking the key once. Second, even with the agent running, Git Bash's *own bundled* SSH client (MinGW's, `/usr/bin/ssh`) has no way to reach the Windows named-pipe agent that PowerShell's SSH client can see — two different SSH implementations on the same machine, only one of which was agent-aware. Diagnosed by directly comparing `ssh -v` output between Bash and PowerShell rather than guessing, which showed the exact same key being offered but only succeeding from PowerShell. Fixed durably by pointing `git config --global core.sshCommand` at the Windows OpenSSH client, so every tool (Bash, PowerShell, any GUI client) uses the one that actually works. **Same shape of lesson as Phase 5's `/config` bug:** two things sharing a name or role (two SSH clients, two `/config` directories) doesn't mean they share the same underlying capability — worth checking directly, not assuming.

## Phase 8 — Clearing the outstanding-work backlog in one pass

With the GitHub/credential issues resolved, the remaining items from the last handoff got built in sequence, each following the same "reviewed carefully, flagged what's unverified" discipline as everything before it: Body Composition Import (§14, packaged 2.1.3), the GoDaddy status page (§15, packaged 2.2.0), and the weight deviation chart (§16, packaged 2.2.1) — see "Where this leaves things" below for each one's real status. `PROMPT.md` — requested a while back, never written — was also finally produced: concrete current-state facts only, deliberately without the history this file exists to hold.

**One new pattern worth naming, since it recurred across all three built features:** where a plan doc left something genuinely undecided (the status page's HA `/api/config` enrichment, the overdue-detection formula, the body-comp flow's unknown-row-count workaround), the choice made was written down as an explicit, flagged decision rather than silently picked — same instinct as Phase 5's "never guess at cross-container behavior," applied here to *design* gaps instead of *runtime* bugs. Whether each of those flagged calls was the right one is still Ward's to weigh in on.

## Phase 9 — Icons, four flagged decisions closed out, and the app grows an identity

Several smaller rounds, each following the pattern already established: build what's asked, flag what's genuinely uncertain rather than guess, keep the docs current as the ground truth changes.

**Icons, twice.** First pass: Ward supplied one large `wardstock.png` (a new brand direction — a retro rock-poster "WARDSTOCK" mark, replacing the original peace-sign/keytar logo), resized down to the four served sizes with `System.Drawing` since no image library was available in the build environment. Second pass, days later: Ward supplied his own pre-sized, higher-fidelity versions of the same four sizes (with a "Presented by LeeWard" ribbon added) — copied in directly, no resampling needed. Both passes were honest about the same real limitation: the design is detailed enough that the 32×32 favicon reads as a barely-legible color blob regardless of source quality — a property of the artwork's density at that size, not a resizing defect, and not silently smoothed over as fixed.

**Four things `PLAN.md`/`PROJECT_PLAN.md` had explicitly flagged as needing Ward's call got asked and closed out in one batch**, rather than sitting as permanently-open questions: the two-config-files design (Ward's answer — narrower than a full merge — see below), remote HA panel access (Nabu Casa), the Status Heartbeat's HA-category signal (confirmed staying heartbeat-execution-only, no `/api/config` enrichment), and incident overlap validation (yes, add a non-blocking warning — built).

**Config consolidation — a case of the original recommendation being *available* but not *taken*.** `PLAN.md` §3 had recommended keeping `config.php` and `lucius_secrets.json` fully separate, citing a real chicken-and-egg problem (two different machines, no way to share one literal file). Ward's answer wasn't "keep two files" — it was "make GoDaddy the source of truth," which turned out to have a genuine, buildable middle path once actually discussed: not a full merge (which would've meant duplicating DB credentials into HA's file, the exact blast-radius problem the original design avoided), but a new endpoint (`api/get_shared_config.php`) that lets HA fetch just the two values that were already being hand-duplicated (`OURA_CLIENT_ID`/`SECRET`) fresh on each relevant run, instead of storing a local copy. `API_SYNC_TOKEN` remains the one unavoidable bootstrap secret — a token can't hand out the credential that authenticates fetching it, so that duplication was never solvable and isn't pretended to be. **Worth naming as its own small lesson:** presenting a flagged decision as binary (keep the recommendation vs. accept the tradeoff) can miss a real third option that only surfaces once the person who actually has to live with it says what they're really trying to solve.

**The app grew a public identity — About page, and the marketing flyer folded in.** Two rounds: first, `about.php` (app description, version, LeeWard company blurb, founder cards for Ward and Lisa Bowman using a cropped round LeeWard emblem as a shared placeholder photo, Lisa's bio explicitly deferred). Ward then asked for the marketing flyer to stop being a separate standalone artifact and ship as part of the app itself — `marketing/leeward_wardstock_flyer.html` moved (not copied) into `godaddy/app/marketing.html`, safe to relocate since it was already fully self-contained (fonts via CDN, logo as base64, no relative paths). Both pages made public (no login) and linked from `login.php`'s footer, matching the existing Privacy/Terms precedent rather than inventing a new pattern. **One real near-miss caught mid-build, not after:** Ward said he'd already dropped an "About Ward" bio file for this — it genuinely wasn't there yet. Rather than write a placeholder bio from general knowledge of the name, the page shipped with an explicit `<!-- TODO -->` and a plain "bio coming soon" until the real file actually arrived a few messages later (and was then used close to verbatim, since it was a real, complete, well-written bio — not something to paraphrase into possibly-wrong specifics about a real person's career).

**And a real bug, caught in production right after that move shipped.** `marketing.html` came back a 500 on GoDaddy. Ward reported it with the actual server response body and a screenshot rather than just "it's broken" — which made the diagnosis fast: cPanel's own generic error page, not a PHP error, and the one thing unusual about this specific file was its size (~2MB, versus everything else in `app/` being a few KB). Both logo images had been embedded directly as base64 `data:` URIs, which is exactly what made the original move "safe to relocate, no relative dependencies" — but that same choice made the single static response too large for GoDaddy's shared-hosting stack to serve. Fixed by extracting both images back out to real files, referenced normally — the page dropped from ~2MB to ~17KB. **Genuinely reverses part of the previous entry's reasoning:** "fully self-contained" was true and also, it turned out, the actual cause of the failure — worth remembering that a property praised as a strength in one context (nothing to break by moving it) can be exactly the liability in another (a hosting platform with an undocumented size ceiling).

**Two new working conventions adopted here, process rather than product:** version bumps and `git push` now happen only when Ward explicitly says so, not automatically after every change (batches of unrelated work accumulate locally between pushes); and `ForClaude/`/`ForWard/` as standing drop folders — Ward drops files to be processed into the former, Claude moves them to the latter once used, keeping the inbox clean without either folder ever being git-tracked.

## Phase 10 — Repo split, Fulgrim's app-layout gaps, and closing out the Flux engine end to end

The biggest single batch yet, spanning a full session: a workspace restructure, two rounds of new GoDaddy features, a validation pass that found the project's own status docs had drifted from reality, and finally the piece Fulgrim had been building toward since Phase 9 — the Flux analysis engine and its chart rendering, both built and reasonably tested without ever touching a live InfluxDB.

**Repo root moved out from under the shared workspace.** Ward had already physically moved `godaddy/`/`homeassistant/`/`marketing/` into a `Wardstock/` subfolder by hand, planning ahead for more sibling projects (a Kardia EKG effort, a manufacturing-app exploration) to live alongside it without being folded into this repo. The git side hadn't caught up — `.git` was still rooted one level up. Turned out to need no history rewrite at all: the paths already matched the new layout, so it was a straight relocation (`.git` moved, a `pre-restructure-backup` tag left as a rollback point), not a `filter-repo` job. `ForClaude/`/`ForWard/`/`ClaudeMemory/` stayed at the shared workspace root as Ward asked, now one level up from this repo rather than gitignored siblings inside it.

**Two new GoDaddy features, decided through actual back-and-forth rather than assumed.** An "attention needed" reminder system (missed medicine, no weigh-in, therapy notes overdue past a 5pm cutoff, Oura sync gone stale) — Ward's own spec, refined in conversation: snoozable but only until the next calendar day, a blinking icon rather than a permanent nav item, and a separate "proposed correlation events" queue for whenever the Flux engine starts producing hypothesis-style suggestions. Blood pressure tracking followed the same pattern — a real design fork (one value/day like weight, or multiple timestamped readings) resolved by asking rather than guessing, landing on a dedicated table so a real morning/evening routine doesn't collapse into one number.

**A validation pass turned up something worth naming: this project's own status docs had drifted from what was actually built.** `CLAUDE.md`'s outstanding-work note said the Where When nav, the Oura self-heal fix, Medical History Import, and the wherewhen backup/restore flows were all still to build — checking the actual files against `PLAN.md`'s own claims showed they'd already shipped in an earlier, undocumented pass. Corrected twice over the course of the session as more got checked. Real, if narrower, gaps did turn up alongside the false ones: three newer flows (Medical History Import, wherewhen Data Export, wherewhen Data Restore) had no `job_failed` path at all — fixed with a `catch` node feeding the same failure-logging pattern the older flows already used, and folded into the Status Heartbeat so all of them (eventually seven) report through `status.php`.

**The Flux analysis engine — the thing Fulgrim's whole "wherewhen" framing has been pointing at since it was named — got built in one pass, close to the whole ~20-analysis plan at once, deliberately without a mid-point check-in.** Real field/measurement names were pulled from the other flows' own InfluxDB-write code, not the plan doc's prose. Flux itself stays to `from|range|filter|sort`; the actual statistics (correlation, trend slope, clustering) run in plain JS afterward, since Flux's own stats packages were never confirmed against this project's real install and a hand-written function is something that can actually be tested. And it was — no live InfluxDB existed to test against, so testing meant syntax-checking every embedded function body, simulating the full pipeline against mocked responses, and a companion test flow against synthetic fixtures, the same discipline as every other untested-but-reviewed flow in this project, just pushed further than usual because the stakes (twenty interconnected functions, not one) justified it. That effort caught real bugs before they ever reached Ward: two shape functions silently mixing data from the wrong measurement, two real gaps in what `godaddy_pull_flow.json` was syncing to InfluxDB at all (medication adherence, night-waking notes), and — found while adapting it — a pre-existing bug in the restore flow's CSV parser that had been sitting there since Phase 9's Fulgrim groundwork, where a repeated header row across Flux table blocks silently misparsed as data. Chart rendering on `analysis.php` followed the same close-the-loop instinct: every one of the ~20 result shapes cross-checked field-by-field against what the engine actually produces, not assumed from the shape functions' own docstrings.

**Nothing in this phase has run against Ward's real HA instance** — same standing caveat as every phase since Phase 5, and the one thing none of this session's testing could substitute for.

## Where this leaves things

- **GoDaddy side:** stable, versioned, fully built for everything decided so far (**2.2.6 as of this writing**). No known credential exposure — `config.php` is gitignored and scrubbed from history; DB password rotation in cPanel is Ward's own remaining action. Database upgrades now run through two cumulative files (`sql/upgrade_from_1.0.0.sql`, `sql/upgrade_from_2.0.0.sql`) instead of an accumulating pile of per-release `alter_*.sql` fragments — see item 61 in `PROJECT_PLAN.md`. Now has a public identity beyond the login form: `about.php` and `marketing.html`, both linked from `login.php`'s footer — see Phase 9.
- **HA side:** system-test-confirmed working end to end (config, InfluxDB, Oura reachability, GoDaddy reachability+auth+version-sync all green) with the real 2.x InfluxDB add-on. All **four** scheduled flows (Oura Sync, GoDaddy Pull, Body Composition Import, Status Heartbeat) are built but not yet run for real — the next real milestone.
- **Body Composition feature:** built (`homeassistant/nodered/body_comp_import_flow.json` + `godaddy/app/api/weight_push.php`, packaged as 2.1.3) — same "reviewed carefully, never run against a live stack" status as the other two sync flows, plus one open design gap: a real export's row count isn't known ahead of time, and the flow's workaround (an oversized `readRange` request) hasn't been checked against a real oversized read.
- **GoDaddy status page (§15):** built (`status.php` + `api/status_push.php` + `nodered/status_heartbeat_flow.json`, packaged as 2.2.0) — same unverified-until-run status as the other flows, plus one deliberate scope decision: the "HA" category's signal is the heartbeat flow's own execution, not a real HA `/api/config` call (would need an auth mechanism — Supervisor token or long-lived access token — this project doesn't otherwise use; flagged as an open follow-up needing Ward's choice, not silently skipped).
- **Weight deviation chart (§16):** built (`weight_deviation.php`, packaged as 2.2.1) — no HA/Node-RED dependency, so unlike the other two this one carries no "unverified against a live stack" caveat.
- **`PROMPT.md`:** written — concrete rebuild facts, no narrative (that's this file's job).
- **Marketing flyer:** no longer a separate artifact — lives at `godaddy/app/marketing.html`, ships with the app, public, linked from `login.php`. **No longer self-contained** — the two logo images live alongside it as real files (`marketing-mark.png`/`marketing-emblem.png`) after the base64-embedding-caused-a-500 fix; all three files need to ship together. `marketing/` holds only the original source logo PNG and docs. A PDF can still be generated on demand via headless Edge/Chrome rather than `wkhtmltopdf` (not installed in this environment) — real Google Fonts loaded instead of the local-font substitutes the original `wkhtmltopdf` approach needed, and the known `border-radius`-collapses-the-table bug doesn't apply to this rendering engine regardless. Never committed to git either way (gitignored, generate-on-demand).
- **About page:** built and public (`about.php`) — app description, version, LeeWard company info, founder cards for Ward and Lisa Bowman. Ward's bio is real and complete; Lisa's is deliberately deferred, her own call.
- **App identity/branding:** current logo is the "WARDSTOCK" retro rock-poster mark (replacing the original design), served at all four standard sizes from Ward's own higher-fidelity source. 32×32 favicon legibility remains a known, undecided-whether-worth-fixing limitation.
- **Repo structure (Phase 10):** this repo now lives rooted at `Wardstock/`, one level inside Ward's shared multi-project workspace, not at that workspace's own root — see `Wardstock/CLAUDE.md`'s "Repo root moved to Wardstock/" note. Future unrelated projects get their own sibling folder and their own repo, not folded in here.
- **Fulgrim (3.x), functionally complete as of Phase 10 — packaged 3.2.0, GoDaddy side confirmed live.** GoDaddy side: the "Where When" nav consolidation, the attention/reminder system, blood pressure tracking, and the ~20-analysis chart rendering on `analysis.php` are all built — **and deployed**: Ward ran `sql/upgrade_from_3.0.0.sql` in phpMyAdmin and uploaded `app/`/`api/` to `public_html/Wardstock/`, both confirmed working right after. HA side: all planned flows exist (Oura Sync, GoDaddy Pull, Body Composition Import, Status Heartbeat, Medical History Import, wherewhen Data Export, wherewhen Data Restore, and now the Analysis Engine — eight total), each with a `job_failed` path and Status Heartbeat coverage. The Analysis Engine (`nodered/analysis_engine_flow.json` + companion test) is the one piece that didn't exist before this phase — see Phase 10's own account of how it was built and tested without live infra. **Nothing in this project's HA side has ever been run against Ward's real Home Assistant instance** — now the single remaining piece of the entire Fulgrim build, unchanged as an open item since Phase 5.
