# WardStock — Project Plan

**Purpose of this file:** a running snapshot of what WardStock is, what's built, and what's next — so a future session can read this instead of us re-deriving context from scratch. Upload this file (or paste its contents) at the start of a new conversation on this project.

## What WardStock is

A private, single-user, password-protected PHP + MySQL health-tracking app, hosted on GoDaddy shared hosting at `public_html/Wardstock/`. Named after Ward's real "WardStock" birthday party. Sections: Incidents (anxiety/cardiac), Daily Log, Medications, Therapy (sessions + recurring schedule + report), a 7-day dashboard, and JSON export. Built for CBT/anxiety pattern-tracking alongside Ward's therapist.

**See also `../homeassistant/PLAN.md`** — a separate, not-yet-started plan for syncing WardStock with a Home Assistant instance (Node-RED + InfluxDB) that will handle high-fidelity Oura data and analytics/correlation, while GoDaddy stays the always-reachable system of record for anything hand-entered. Will eventually require new API endpoints on the WardStock side (§5 of that doc) — not built yet.

No framework — plain PHP, PDO/MySQL, vanilla CSS/JS. **Confirmed not multi-user** (Aug 2026): one shared login, no `user_id` column anywhere. Documented in README under "Is this multi-user?" — flagged as a real (not trivial) change if ever needed.

**Database tables:** `incidents` (category, start/end time, nitroglycerin flag), `daily_logs` (steps/exercise/standing minutes, caffeine/alcohol servings, medication checklist JSON, state of mind), `medications` (name, dosage, med_type scheduled/as_needed, cadence, start_date, end_date), `therapy_sessions`, `therapy_schedules` (recurrence), `app_settings` (last_export_at), `app_user`.

**Known design decisions worth remembering:**
- Ward's real DB credentials live in the shipped `config.php` — never reset to placeholders when regenerating.
- Server folder is cased `Wardstock` (capital W) — case-sensitive hosting.
- **Schema mode: additive `alter_*.sql` again as of Aug 2026** — Ward now has real data (active incidents, medications) worth preserving, so we moved back from the earlier clean-slate rebuild. schema.sql/reset_clean.sql are kept in sync for fresh installs, but any change to an *existing* install ships as a standalone alter script.
- Medications seeded from `ward_private_medical_journal_r001.md`: Amlodipine, Aspirin, Ezetimibe, Rosuvastatin, Duloxetine (all daily/scheduled), Repatha (biweekly/scheduled), Wegovy (weekly/scheduled), Nitroglycerin (as-needed — logged via Cardiac incidents, not the Daily Log checklist).
- A dosage change = a new `medications` row (with its own start date), not an edit — preserves history. The "Start a new dosage" link automates closing the old row.
- Medication dashboard/daily-log completeness is date-aware: uses the medications valid *on that specific date*, not "today" — so backfilling a past day checks against what was actually prescribed then.
- Caffeine/alcohol/exercise are event-based (not expected every single day) but still show red when never entered for a day — the color grading (green/amber/red, plus black for alcohol=0) only applies once a value exists.
- Therapy due-date math: `(day - schedule.start_date) % frequency_days == 0` — verified correct via a standalone Python equivalent (no PHP CLI available in the build sandbox to test directly).

50. **Second real bug found and fixed in `oura_fetch_day()`, again from Ward's live testing — this is a genuine code fix, not just diagnostics this time.** After the scope fix, the range scan (item #48's confirmation) proved real data exists, but Ward's actual "Pull from Oura" for Aug 12 specifically still returned "nothing was saved." Root cause, confirmed directly against real returned data: Oura's date-range filter appears to key off when a sleep session *started*, not its `"day"` tag — a session with `bedtime_start` 9:25pm the evening before but tagged `"day": "<target date>"` (the wake day) was being excluded by a single-day `start_date=end_date=<target date>` query, even though Oura itself considers that record to belong to the target date. Fixed by querying a 2-day window (target date − 1 through target date) for all three endpoints, then filtering results to records whose own `day` field exactly matches the target date. **Packaged as 1.1.1.**
51. **Third fix to the same function — the 2-day window from item #50 turned out to still be insufficient.** Ward re-tested with a manual 2-day range scan (Aug 11–12) and the key `long_sleep` record was STILL missing, even though it appeared fine in the earlier 14-day scan. Diagnosed from the actual data: the session's `bedtime_start` is `2026-08-11T21:25:27-04:00` — converted to UTC that's `2026-08-12T01:25:27Z`, i.e. already past midnight into the 12th. Working hypothesis (not confirmed against Oura's actual source/docs, only inferred from behavior): `end_date` is an EXCLUSIVE boundary at the *start* of that date, not inclusive through its end — so `end_date=<the 12th>` cuts off at `2026-08-12T00:00:00`, excluding a session starting 90 minutes later in UTC despite being unambiguously "the night of the 11th" in local time. The 14-day scan never hit this because its `end_date` was days past the target, giving huge buffer. Fixed by widening the window to BOTH sides — `date-1` through `date+1` — for all three endpoints, while keeping the exact-day filter from item #50 intact (so the wider window can't accidentally pull in the wrong day's data). **Packaged as 1.1.2.**
    **Honest caveat for whoever picks this up next:** this is now the third attempted fix for the same underlying issue, and the exclusive-end-date theory is inferred from one data point, not confirmed against Oura's source or documentation (which doesn't address this specifically). If Aug 12 (or any date) still fails to populate after this fix, the range scan tool (`oura_test.php` Section 6) with a deliberately wide, asymmetric range is the next diagnostic step — don't assume this fix is correct just because the reasoning sounds plausible.

### Scheduled server-side data pulls

Right now, pulling Oura data (and any future outside-source pull) requires manually visiting `oura_sync.php` and clicking a button. The idea: a server-side script that runs on a schedule and fetches automatically — e.g., pull yesterday's Oura data every morning without having to remember to do it.

**Feasibility confirmed:** GoDaddy's cPanel (which covers essentially all of their shared hosting) has a native **Cron Jobs** feature under the Advanced section, and it can run a PHP script directly on a schedule — e.g. `php -f /home/<account>/public_html/Wardstock/scripts/oura_daily_pull.php`. This is a standard, well-supported capability, not something GoDaddy would need to specially enable. Worth checking Ward's specific plan tier for any minimum-interval restriction (some budget tiers cap how frequently a cron can fire, e.g. no more than every 5 or 15 minutes) — daily/hourly schedules are universally fine regardless.

Open questions to resolve before building:
- The script would need to run **without a logged-in session** (cron has no browser, no cookies) — needs its own auth path, e.g. reading `config.php` directly rather than going through `auth.php`'s session check. Keep it outside `public_html`'s directly-web-reachable path if possible, or protect it some other way, since a cron-triggered script sitting at a guessable URL with no auth is a real exposure if anyone finds it.
- What should it pull, and for which date — yesterday only? A short trailing window in case a previous run failed?
- Should a failed scheduled pull email/notify Ward, or just log to `oura_tokens`' existing `last_attempt_*` columns for him to notice on his own next visit to `oura_sync.php`/`debug.php`?
- Extend the same mechanism to any other future outside data source, not just Oura.

### Historical analysis / correlation (caffeine, alcohol, incidents) — MOVED

**Decided (see `../homeassistant/PLAN.md`): this now lives on the Home Assistant/InfluxDB side, not as a WardStock/PHP feature.** Ward confirmed HA is meant to be "our processing engine" for this kind of analysis, and InfluxDB's query language is a better fit for range-based correlation work than hand-rolled MySQL aggregates anyway. Don't build this in WardStock — check the HA plan doc for current status instead. ## Working conventions (to minimize usage)

- Small changes ship as: changed file(s) only. Full zip only gets rebuilt when Ward asks for it ("package it" / "give me the zip").
- This plan file is kept current — Completed section grows, "Not yet done" reflects real state — so a new session can start here instead of re-reading the whole chat.
- **Schema changes are back to additive `alter_*.sql`** (not clean-slate) as of this session — Ward now has real data (active incidents, medications) worth preserving. schema.sql/reset_clean.sql are still kept in sync for fresh installs, but the deployable change for an *existing* install is always the standalone alter script.
- **Project structure (Aug 2026, permanent going forward, superseding the "four folders at the top level" note below):** as of item #53, this is a **two-piece project called Lucius**. The zip's top level is now: `godaddy/` (this whole piece — everything described below), `homeassistant/` (the HA sync/analytics piece — see `../homeassistant/PLAN.md`), plus a short top-level `README.md` introducing both. **All of this file's own paths (`app/`, `config/`, `sql/`, `setup-delete-after-use/`) are relative to `godaddy/`, since this file now lives inside it** — don't prepend `godaddy/` when reading instructions elsewhere in this doc, but DO include the `godaddy/` prefix when writing top-level project documentation or instructions from outside this folder.
  - `app/` — every file that runs the site *except* `config.php`, uploaded flat into `public_html/Wardstock/` (contents of this folder, not the folder itself). Safe to blindly re-upload in full every release.
  - `config/` — just `config.php` + a locking `.htaccess`. Uploaded **once**, as its own real subfolder (`Wardstock/config/`, NOT flattened like `app/`) — never re-uploaded as part of a routine update. Whole point of splitting it out: a careless "upload everything in app/" can never overwrite real credentials with the blank template, since routine updates never touch this folder at all.
  - `sql/` — every `.sql` file. Never uploaded via FTP — pasted into phpMyAdmin instead.
  - `setup-delete-after-use/` — `setup.php` and `reset_password.php`. Uploaded temporarily only when actually needed, deleted from the server immediately after — both are unauthenticated action pages, a real security hole if left reachable.
  When building a new zip: create these four subfolders fresh each time (don't assume the working directory already has this structure — rebuild it from the flat file list) and double-check no personal data files (e.g. `ward_weight_import.json`) get swept into `app/` by a wildcard move.
- **Versioning (rev. Aug 2026, permanent going forward):** current is 2.0.0 "Lucius." Scheme changed from `Major.Minor` to **`Major.SQL.Code`** at Ward's request, specifically to stop requiring a database step on every single release (the codename changed again at item #53's major bump — "Sidroh" was the 1.x line, before the project became two pieces):
  - **Major** — genuinely major overhaul only. Resets SQL and Code to 0.
  - **SQL** — bump ONLY in a release that actually changes something in `sql/`. Resets Code to 0. **This is the only number the database tracks.**
  - **Code** — bump for every release that does NOT touch `sql/`. Never bump both SQL and Code in the same release — a release is either "this changed sql/" (bump SQL) or "this didn't" (bump Code), not both.
  - `app_settings.db_version` stores only the Major.SQL portion (e.g. `"1.1"`), never the full three-part version. `debug.php` compares against `APP_VERSION_SCHEMA` (Major.SQL), not `APP_VERSION` (the full string) — a code-only release is expected to show a "different" full version than what's recorded in the database, and that's correct, not a mismatch.
  - **`sql/set_version.sql` only ships in a release when `sql/` actually changed that release.** If a release's zip doesn't include one, there is nothing to run in phpMyAdmin for that release at all — that's the entire point of the new scheme.
  - **One-time transition note:** the stored format itself changed from the old `"1.03"` style to the new `"1.1"` (Major.SQL only) style — this required one more `set_version.sql` run to move to the new format, a one-off exception to "SQL-only releases need a run." Every release after this one follows the rule cleanly.
